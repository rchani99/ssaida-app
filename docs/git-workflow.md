# Git 및 GitHub 버전 관리

개발 결과는 코드 커밋, 검증 기록, 배포 버전을 연결해 추적한다. 기본 브랜치는 `master`다.
이 절차는 기능 착수, 원격 push, 기본 브랜치 병합 또는 배포 권한을 추가하지 않는다.

## 현재 GitHub 승인

2026-10-22 사용자가 이번 `codex/dev02-onboarding`과 `android-beta-v1.0.0-5`의 push 및
Draft PR 생성을 명시적으로 승인했다. 앞으로도 사용자가 착수 승인한 개발 과제의 검수 완료 변경은
관련 작업 브랜치 push, Draft PR 생성/갱신과 배포 소스 태그 반영을 반복 승인 없이 진행한다.
공개 범위 검토와 관련 파일 선택 원칙은 유지한다. 기본 브랜치 `master`/`main` 병합과 실제 배포는
별도 승인을 받는다. 새 과제 착수, force push, 원격 브랜치·태그 삭제 권한은 포함하지 않는다.

## 과제별 절차

1. 현재 Git 상태, 기존 worktree, 원격 브랜치와 열린 PR을 확인한다. 다른 작업의 변경은 보존한다.
2. 승인된 기준 커밋에서 `codex/<과제명>` 브랜치를 사용한다. 의존 기능이 기본 브랜치에 없으면
   그 기능 브랜치를 기준으로 삼고 PR에도 의존 관계를 명시한다.
3. 코드와 관련 회귀 테스트를 함께 커밋한다. 문서 변경은 가능하면 별도 커밋으로 남긴다.
   파일 경로를 명시해 stage하고 staged diff, 공백 오류, 민감정보를 확인한다.
4. 위험에 맞는 테스트와 독립 검수 결과를 기록한다. 과거 검증, 이번 검증, 미실행 범위를 구분한다.
5. 승인된 원격 반영 범위가 있으면 해당 작업 브랜치만 push하고 기존 PR을 갱신하거나 Draft PR을 만든다.
   권한이 없으면 로컬 커밋과 PR 제목·본문·대상 브랜치까지 준비한 뒤 승인을 요청한다.
6. PR에는 문제와 변경 동작, 검증 결과, 남은 위험, 의존 브랜치와 배포 상태를 적는다.
   열린 PR은 앱 작업에 연결한다. 필수 검증이 남으면 검수 대기 상태를 유지한다.
7. 기본 브랜치 병합은 별도 승인 대상이다. force push와 원격 브랜치 삭제도 임의로 수행하지 않는다.
8. 배포 시 `docs/releases/`에 앱 버전·빌드 번호, 정확한 소스 SHA, 빌드 ID, APK 해시,
   배포 결과와 검증 한계를 기록한다. `android-beta-v<버전>-<빌드번호>` annotated tag를
   배포한 소스 커밋에 붙인다. 후속 문서 커밋이나 미배포 변경을 배포 태그에 포함하지 않는다.
   기존 배포 태그는 이동하거나 재사용하지 않는다. 태그 push도 승인 범위에 포함되어야 한다.
9. 작업 보고와 백로그에 로컬 커밋, 원격 반영, PR 검수, 병합, 빌드, 배포를 각각 구분한다.
   로컬 커밋이나 push 성공만으로 제품 과제를 DONE으로 바꾸지 않는다.

## 공개 저장소에 올리는 범위

현재 GitHub 저장소는 공개다. 이번 변경뿐 아니라 새로 push할 전체 커밋 범위를 검토한다.
소스·테스트·공개 가능한 개발 문서를 올리며, 비밀값, 환경 파일, 인증 토큰, 서명 키,
테스터 정보, 기기 화면, 로컬 실행 상태·로그, APK 및 빌드 산출물은 포함하지 않는다.
APK 배포는 승인된 Firebase 경로를 사용한다. 추적 중인 파일은 ignore만으로 제외되지 않으므로
staged 파일 목록을 직접 확인한다. 마케팅·이미지 등 다른 작업의 변경을 함께 stage하지 않는다.
