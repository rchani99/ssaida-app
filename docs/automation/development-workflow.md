- 자동 병합, 운영 DB 변경, 원격 빌드 업로드·배포, 스토어 제출, 외부 게시·연락·초대·결제는 해당 행위에 대한 구체적인 사용자 권한 범위에서만 수행한다. 이미 받은 유효한 권한은 재질문하지 않는다.
- 예약의 활성 상태는 실행 성공과 다르다. PC·앱·권한·사용량·승인 대기로 실행이 지연될 수 있다. 권한을 우회하거나 사용자 채팅에 임의 메시지를 보내지 않는다.

3. 공용 큐의 기본 단일 조정자는 기존 예약 채팅 `01a12eee-6360-7fe1-aa67-3f816397f27d`다. 다른 채팅은 설정 점검·읽기만 하며, 사용자가 다른 채팅에서 수동 실행을 요청했다면 기존 조정자의 중단과 소유권 인계를 확인한 후 작업을 점유한다. `activeTask`가 있으면 소유 채팅/에이전트의 실제 상태, 작업 경로, diff와 기록을 확인한다. 다른 소유자가 실행 중이거나 상태가 불명확하면 새 작업도 점유하지 않고 읽기 전용 확인 후 이번 실행을 종료한다. 중단이 확인되면 기존 변경을 보존하고 소유권 인계를 기록해 이어간다. 시간 경과만으로 잠금을 해제하지 않는다. JSON은 협조용 기록이며 원자적 잠금이나 실행 상태의 증거가 아니다.
4. 승인된 과제만 선택한다. 현재 구현은 명시적으로 승인된 DEV-02이며 DEV-01 Firebase 배포의 남은 검증도 유지한다. DEV-03~06은 그 뒤 별도 승인 범위에서 재개한다. P2/P3는 명시적 착수 승인 전 구현 금지다. 기존 미완료 작업도 현재 승인 범위와 일치할 때만 재개하고 구체적 근거·완료 조건을 정한다.
5. 같은 근거로 조사를 반복하거나 신규 기능을 자율 추가하지 않는다. 작업이 막히면 같은 승인 Sprint의 독립 과제만 진행한다. 마케팅도 별도 승인 범위가 있을 때만 수행하며 개발의 대체 성과로 집계하지 않는다. 실행 가능한 승인 과제가 없으면 조건을 기록하고 대기한다.
6. 회당 주 결과물 한 건을 끝낸다. 조정자가 작업 ID, 소유 채팅/에이전트, 기준 SHA, 경로·소유 파일, 완료 조건, 재개 단계를 `activeTask`에 먼저 저장한다. 최초 점유 직전에 빈 상태를 다시 확인한다. 이후 모든 저장 직전에 작업 ID·소유 채팅·소유 에이전트가 자신의 점유 정보와 일치하는지 확인한다. 다른 조정자가 상태를 변경했다면 공용 상태를 덮어쓰지 않고 종료한다.

## 구현 → 검증 → 독립 검수

1. 조정자는 범위와 완료 조건을 지정하고 구현 담당 subagent에게 위임한다. 검수 담당은 구현 담당과 별개로 생성한다. 동시 보조 최대 2명, 재위임 금지, 모델·추론 설정은 상속한다. 단순 조회에 상시 보조를 만들지 않는다.
2. 개발은 적합한 기존 격리 worktree를 재사용하거나 확인한 기준 SHA로 생성한다. 이번 설정 점검 시 브랜치는 `codex/firebase-deployment`였으나 매 실행 실제 상태와 배포 기록을 다시 확인한다. 원격 기본 브랜치로 임의 변경하지 않는다. 새 브랜치 이름은 `codex/`로 시작한다.
3. 원본의 미커밋 사용자 변경·이미지·다른 작업 결과를 덮어쓰거나 초기화하지 않는다. 필요한 미커밋 변경이 있으면 소유·관련성을 확인해 필요한 파일만 안전하게 반영한다. worktree에 없는 이 운영 지침과 완료 조건은 조정자가 구현/검수 담당에게 직접 전달한다.
4. 구현 담당은 실제 코드와 필요한 회귀 검증을 만든다. 설치·검증 명령은 먼저 읽고 외부 부작용을 확인한다. 의존성 설치가 필요하면 기존 lockfile을 유지한다. 비밀값을 로그·결과물·상태 파일에 쓰지 않는다.
5. 문서·단순 UI는 관련 링크/정합성/화면/파일의 최소 검증으로 충분하면 전체 회귀를 반복하지 않는다. TypeScript 변경은 타입 검사·관련 린트를 선택하고 DB·RPC·인증·결제·삭제 변경은 관련 격리 회귀를 수행한다. 넓은 영향에는 `pnpm test`를 검토한다. 과거 실행에서 pnpm wrapper의 예상치 못한 설치 로그가 있었으므로 명령/런타임을 확인하고 필요하면 설치된 Node CLI를 직접 사용한다. 기존 실패와 이번 변경 실패를 구분한다.
6. 현재 `pnpm test`는 `scripts/run-regressions.mjs`를 실행한다. 이 러너는 DB 전용 테스트를 제외하고 혼합 스크립트에 `--ui-only`를 전달한다. 실제 API·DB·실기기·빌드 통과를 뜻하지 않는다. 각 스크립트가 플래그를 준수하는지 실행 전 확인한다. `*.test.mjs` 등 러너가 포함하지 않는 관련 검증은 별도로 선택한다. 네이티브 설정이나 UI를 바꾸면 가능한 로컬 빌드/시각 확인을 추가하되 없는 실기기 결과를 만들지 않는다.
7. 검수 담당에게 작업 경로, 기준 SHA, 실제 diff(새 파일 포함), 완료 조건, 실행한 명령·결과·미실행 이유를 전달한다. 검수자는 수정된 파일의 실제 내용을 읽고 기능 정확성, 회귀, 데이터 보호, 테스트 사각지대, 범위를 검토한다. 실행/빌드 결과만 보고 승인하지 않는다.
8. 지적 사항은 구현 담당이 수정하고 검증·독립 재검수한다. 회당 수정 최대 2회, 같은 도구 오류 재시도 최대 1회. 필수 지적이나 검증이 남으면 완료 금지다. 검수 도구가 없으면 승인 범위의 구현·자체 검증 후 `REVIEW`(독립 검수 대기)로 남긴다.

## 결과와 재개

- 과제 실행 승인과 큐 이관 후 조정자만 공용 상태와 개발 백로그를 갱신한다. 단계별 승인 근거·재개 정보를 저장하고 과거 결과를 덮어쓰지 않는다. 기록 위치는 `docs/automation/runs/<작업ID>-<실행ID>.md`다.
- 실행 기록에는 문제·근거, 기준 SHA와 작업 경로/브랜치, 변경 파일, diff 또는 패치 위치, 검증 명령·종료 코드·결과·누락 범위, 검수 담당/결론/남은 지적, 수정 횟수, 다음 단계를 포함한다. 미추적 파일도 결과에 포함하고 비밀값은 제외한다. 파일이 존재하는지 확인한 다음 상태를 바꾼다.
- 새 과제 상태는 `TODO / IN_PROGRESS / BLOCKED / REVIEW / DONE`이다. 분석·구현·검증은 세부 단계다. 구현 저장·필수 로컬/운영 검증·독립 검수·완료 조건이 모두 충족돼야 DONE이다. 배포·병합·실기기는 별도 기록한다. 과거 JSON의 `reviewed` 등 소문자 상태는 역사 이력이며 새 과제 DONE으로 변환하지 않는다.
- 실행이 끝나거나 보류될 때 작업 ID·소유 채팅·소유 에이전트가 자신의 점유 정보와 일치하는지 다시 확인한 후에만 `activeTask`를 비우고 해당 큐 항목에 경로·재개 단계·결과를 남긴다. 타인의 점유는 해제하지 않는다. 프로세스 중단으로 남은 `activeTask`는 다음 실행이 실상태를 확인해 복구한다. 검수된 worktree는 병합 대기 상태로 보존한다.
- 다음 실행도 승인 범위와 DEV-01 우선순위를 먼저 확인한다. 승인된 과제의 미검수 결과부터 처리하고 완료된 변경은 반복하지 않는다. 기존 worktree 결과를 재사용하면 기준/의존성을 기록하며 사용자 브랜치로 자동 병합하지 않는다.
- 외부 입력 조건과 마지막 근거를 기록하고 동일 승인 범위의 독립 작업만 한다. 새 근거 없이 같은 실패·질문을 반복하지 않는다. 큐가 비었다고 신규 기능을 등록·구현하지 않고 필요성을 제안한다. 승인 과제가 없으면 대기한다.
- 보고는 완료물·다음 작업·필요한 사용자 판단의 최대 3항목이다. 새 검수 완료물·의미 있는 실패·필수 사용자 행동이 있을 때 알리고, 변화 없는 대기는 알리지 않는다. 정오의 기존 짧은 일일 요약은 유지한다.
