# 측정·신청 정보 운영

## 실제 사용 측정

`202610090002_pilot_core_cycles.sql`은 아이 완료 후 부모가 확인한 첫 시각을 공부별 1회 기록한다. 이름·이메일·답안은 저장하지 않는다. 부모 확인 결과 PARENT_CONFIRMED/PARTIAL/RETRY는 모두 **관리 흐름 사용**으로 집계하며 학습 성공이나 이해도를 뜻하지 않는다. SKIPPED는 제외한다. 같은 과제를 다시 확인해도 한 번만 센다. 과제 삭제 후에도 운영 집계는 보존되지만 부모 계정 삭제 시 함께 삭제된다.

마이그레이션 적용 이후만 측정하며 과거 기록을 임의 복원하지 않는다. 파일럿 모집 전에 적용하고 실제 가입 전 테스트 데이터를 집계에 넣지 않는다. 새 테이블은 일반 앱 사용자에게 읽기/쓰기 권한이 없고 운영용 서비스 역할만 조회·삭제한다. **운영 DB 적용은 별도 배포 단계이며 이 파일을 작성한 것만으로 계측이 시작되지 않는다.**

- 가입: `profiles.created_at`(현재 가입 시 프로필이 만들어지는 시각)
- 활성화: 가입 시각부터 정확히 7×24시간 이내 첫 유효 핵심 흐름. 7일 경계는 제외.
- 반복 사용: 활성화한 한국 시간 주간 다음 **월요일 00:00~다음 월요일 00:00**에 서로 다른 2일 이상. 다음 주가 다 지나지 않은 가족은 분모에서 제외.
- 가격 대상 3회: 서로 다른 공부 과제의 첫 핵심 흐름 3개. 하루 여러 과제도 3회가 될 수 있으므로 주간 재사용과 별도로 본다.
- 유료: 스토어의 실제 결제 성공. 테스트 구매·사전예약·가격 응답은 제외. 계정당 고유 가족 수를 세고 환불 고객은 따로 표시.

## 읽기 전용 내보내기

환경 변수 `PILOT_SUPABASE_URL`, `PILOT_SERVICE_ROLE_KEY`, `PILOT_EXPORT_SALT`를 운영자 환경에 설정한다. 비밀 값은 명령줄·저장소·운영표에 쓰지 않는다. salt는 32자 이상 고정 비밀값. 비공개 코호트 JSON에는 체험에 참여한 부모 profile UUID 배열만 넣는다. 파일과 결과는 저장소 밖의 비공개 경로에 둔다.

```powershell
node scripts/pilot-metrics.mjs --server '<비공개 코호트 JSON 절대경로>' '<새 결과 JSON 절대경로>' '2026-11-01T15:00:00Z'
```

위 날짜는 사용법 예시이며 실제 집계 시각으로 교체한다. 스크립트는 서버를 변경하지 않는다. 결과에는 HMAC 가명 가족 코드, 사용 횟수, 활성화·관찰 종료일·반복 일수만 들어간다. 원본 UUID↔가명 코드↔신청 DB의 연결은 운영자가 비공개 관리한다. 내려받은 데이터도 개인과 연결 가능한 운영 정보로 취급한다. 계정 삭제/철회 시 기존 내보내기에서도 해당 행을 삭제한다.

운영표 ‘가족’에 결과를 옮긴다. 날짜 필드는 **한국 시간으로 변환**해 입력하고, 7일 경계 판정은 JSON의 activated를 최종 기준으로 삼는다(엑셀에 날짜만 넣으면 시간 정보가 사라짐). 동기화 자동화와 결제 서버 연결은 아직 없다. 현재 결제는 운영표에 실제 거래를 수동 기록하는 단계다.

로컬 fixture 검증: `node --test scripts/pilot-metrics.test.mjs`.

로컬 Supabase DB 검증: `node scripts/pilot-db-regression.mjs`. `supabase_db_ssaida-app` Docker 컨테이너에서 마이그레이션과 fixture를 한 트랜잭션으로 실행하고 롤백한다. 2026-10-09 실행에서 최초 확인 기록, 재시도 중복 제외, 건너뛰기 제외, 일반 사용자 권한 제한, 계정 삭제 시 함께 삭제를 확인했다. 운영 DB는 변경하지 않았다.

## Site 신청 데이터

`applications` 테이블에 부모 이메일, 학년, Android 가능 여부, 경로·모집 코드, 불편 사항, 동의 버전, 접수·만료 시각을 저장한다. 브라우저에는 신청 목록 API를 제공하지 않는다. 서버는 입력 길이·필수 동의·같은 출처를 검사하고 중복 이메일은 덮어쓰지 않는다. 신청 성공 응답으로 기존 신청 여부를 구별할 수 없다. 개인정보를 요청 로그에 기록하지 않는다.

Site 소유자는 Sites의 데이터베이스 도구/관리 화면에서 신청 목록을 조회한다. 최초 공개 전 실제 본인 신청을 조회·삭제하고 이메일 안내 발신 계정을 마련한다. 발송 자동화는 구현하지 않았다.

보관 운영: 접수 후 최대 90일. 매주 만료 예정(향후 7일 이내) 신청을 확인해 미리 삭제하고, 철회 요청은 본인 확인 후 지체 없이 삭제한다. 서버는 새로운 신청이 들어오면 만료된 행을 추가 정리한다. 이는 요청 시 정리이며 **정기 삭제 작업은 아니다**. 주간 운영을 중단할 때는 남은 개인정보를 정리한다. 원자료를 내려받았다면 복사본도 함께 삭제한다.

```sql
-- 운영자가 비공개 데이터 관리 도구에서 대상과 개수를 확인한 후 실행.
select id, expires_at from applications where expires_at <= strftime('%Y-%m-%dT%H:%M:%fZ', 'now', '+7 days');
-- ISO 날짜는 문자열 형식을 통일해 비교한다.
delete from applications where expires_at <= strftime('%Y-%m-%dT%H:%M:%fZ', 'now', '+7 days');
```

## 다음 유료 단계

선정 상품의 결제 기능이 생긴 뒤 서버 검증된 거래를 내보내기에 연결한다. 매출·환불·수수료·사진 비용·서버·직접 운영비를 차감한다. 갱신은 두 번째 결제일이 도래한 가족만 분모로 잡는다. 현재 구현은 결제권한·사진 업로드를 만들거나 과금하지 않는다.
