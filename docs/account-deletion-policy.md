# 계정 삭제 정책과 운영 절차

> 2026-10-22 구분: 아래는 **기존 14일 유예 구현·운영 이력**이다. 최신 목표는
> [제품 결정 PD-02](product-decisions.md)의 이메일 인증·최종 동의 후 즉시 실행이며 DEV-03은 미완료다.
> 기존 절차는 현재 운영 실행 권한을 부여하지 않는다. 임의 전환·배포하지 않는다.

최종 검토: 2026-10-18. 적용 대상은 쌓이다 앱의 계정·학습 데이터다.
운영 배포 증거는 [운영 DB 배포 기록](production-db-deployment.md)에 기록한다.

## 사용자에게 제공하는 정책

- 부모님 모드 → 설정 → 계정 삭제에서 삭제 범위와 복구 불가를 확인하고 요청한다.
- 부모와 아이가 기기의 로그인 세션을 공유하므로 실수에 대비해 서버 접수 후 14일을 기다린다.
  대기 중 앱 전체에 안내를 표시하며 기존 데이터와 기능은 유지한다.
- 14일이 지나면 매시간 실행하는 예약 작업이 삭제를 시작한다. 앱을 다시 열거나 요청을
  확정할 필요가 없다. 처리 지연이나 장애가 있어도 요청은 자동 만료되지 않는다.
- 처리 시작 전에는 설정에서 요청을 취소할 수 있다. 서버가 삭제 작업을 확보한 순간부터는
  취소할 수 없다. 이미 처리 중인 요청은 다시 접수하거나 대기 기간을 새로 시작하지 않는다.
- 로그인 계정, 부모 프로필·PIN, 아이 정보, 공부 항목·계획·기록, 컬렉션·성장 기록,
  해당 가족의 파일럿 이용 계측을 함께 삭제한다. 다른 가족의 데이터와 공용 카탈로그는 유지한다.
- Google 계정 자체는 삭제하지 않는다. 삭제 후 Google로 다시 가입하면 새 계정이며,
  이전 학습 기록은 복구되지 않는다. 로그아웃·앱 제거만으로는 계정이 삭제되지 않는다.
- 삭제 완료가 확인된 기기는 예약 알림·알림 설정·메모리 캐시·로컬 세션을 정리한다.
  오프라인 기기는 다시 실행하고 서버의 완료를 확인할 때 정리한다.
  응답 유실·로그인 만료만으로 삭제 완료를 추측하지 않는다.

## 데이터와 보관 범위

| 종류                            | 처리                                                                                                                                        |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 서비스 중인 DB 계정·학습 데이터 | Auth hard delete와 FK cascade로 삭제                                                                                                        |
| 삭제 요청 기록                  | 대기·처리 중 유지, 계정 삭제와 함께 삭제. 취소 요청은 기존 만료일 24시간 후부터 정기 정리                                                   |
| 삭제 결과 확인용 영수증         | 무작위 ID·비밀값의 해시·상태·시각을 저장. 삭제 트랜잭션에서 계정·요청 UUID 제거                                                             |
| 영수증 조회 기간                | 새 영수증은 `max(기존 요청의 21일 시점, 발급 시각) + 30일`까지 유효. 조회가 유효 기간을 연장하지 않음                                       |
| 만료 영수증                     | 만료 24시간 후부터 매시간 최대 1,000건 정리. 정리 장애·적체는 운영 점검 대상                                                                |
| 기기에 저장된 조회 영수증       | 취소·만료 확인 또는 삭제 후 기기 정리 완료 시 제거                                                                                          |
| Supabase Storage                | 현재 앱은 사용자 파일 업로드를 구현하지 않음. 도입 전 별도 삭제 처리를 구현해야 함                                                          |
| DB 백업·플랫폼 운영 로그        | 서비스 DB 삭제와 별도인 인프라 보관 대상. 즉시 물리 소거를 약속하지 않음. 공개 개인정보처리방침에는 실제 프로젝트 보관 설정을 확인하여 기재 |
| 외부 체험 신청·내보낸 자료      | 앱 DB와 별개. [마케팅 자료 보관 절차](marketing/measurement.md)에 따라 별도 삭제                                                            |

영수증은 삭제 결과 조회만 허용한다. 삭제나 PIN 변경을 승인하지 않으며, 원문 비밀값을
DB·로그·URL에 기록하지 않는다. 만료된 영수증으로 완료를 확인할 수 없을 때도 로컬 학습
데이터를 임의로 지우지 않는다. 안내된 로그아웃 경로를 제공하며 재가입을 복구로 안내하지 않는다.

## 서버 계약

- Edge Function만 Auth Admin hard delete API를 호출한다. 앱의 계정 작업마다 Auth `getUser`
  및 연결된 Google identity를 확인하며 요청 본문의 사용자 ID는 받지 않는다.
- `request_sensitive_action`은 기존 대기 요청을 그대로 반환한다. PIN 재설정을 새로 요청해도
  진행 중인 계정 삭제 기록은 제거하지 않는다.
- 삭제의 `expires_at`은 이전 클라이언트와의 응답 호환성을 위해 남겨 둔 값이다. 서버의 삭제
  요청·목록·처리 가능 여부는 이 값으로 만료시키지 않는다. PIN 재설정은 기존 72시간 대기와
  이후 7일의 실행 기한을 유지한다.
- `prepare_delete`로 수동 삭제의 영수증을 받고 기기에 먼저 저장한다. `delete`는 원자적으로
  요청을 확보한 뒤 Admin API를 호출한다. 수동 실행용 영수증의 실행 기한과 조회 기한은 별개다.
- `/purge`는 전용 무작위 bearer만 받는다. 서버가 기록한 대기 시간이 지난 요청만 처리한다.
  실행당 최대 25건·20초 예산이며, 실패하면 HTTP 503과 비식별 상태를 반환한다.
- Admin 호출 실패·프로세스 종료 후에는 확보한 요청을 보존하고 최소 1시간 후 재시도한다.
  아직 시도하지 않은 요청을 먼저 처리하여 실패 계정 하나가 다른 삭제를 계속 막지 않게 한다.
- 취소와 삭제 확보는 같은 행의 잠금으로 직렬화된다. 삭제 결과 기록은 Auth 삭제와 같은
  트랜잭션으로 확정한다. 일반 앱 역할에는 관리 RPC·영수증 테이블 접근 권한이 없다.
- 기존 정책에서 이미 만료된 미처리 요청은 새 마이그레이션이 취소 처리한다.
  과거 요청을 소급하여 삭제 대상으로 되살리지 않는다.

## 운영 설치와 점검

1. 공통 마이그레이션과 운영 전용 마이그레이션을 합친 배포 폴더에서 dry-run 후 적용한다.
   마지막 파일은 `202610180001_durable_account_deletion.sql`이다.
2. `ACCOUNT_ACTIONS_ENABLED=false` 상태로 최신 `account-actions`를 배포한다.
   `verify_jwt=false`는 함수가 직접 인증하는 구조에 필요하다. 공개 상태 조회도 이 함수를 사용한다.
3. 32바이트 이상의 무작위 `ACCOUNT_ACTIONS_PURGE_SECRET`을 서버에 저장하고 동일 값을
   Vault의 `account_actions_purge_secret`에 넣는다. Vault의 `account_actions_purge_url`은
   해당 운영 프로젝트의 `/functions/v1/account-actions/purge` 주소다.
4. `supabase/snippets/account-deletion-schedule.sql`을 실행한다. 자동 삭제는 매시 00분,
   오래된 요청·영수증 정리는 매시 15분에 실행한다. UTC cron이며 한국에서도 매시 같은 분이다.
5. 두 작업의 활성 상태를 확인한 뒤 `ACCOUNT_ACTIONS_ENABLED=true`로 활성화한다.
   이 플래그는 PIN 복구도 활성화한다. `PIN_RECOVERY_ENABLED=true`를 별도로 유지하면
   삭제를 비활성화해도 PIN 복구는 사용할 수 있다.
6. `supabase/snippets/account-deletion-health.sql`로 due·가장 오래된 예정 시각·예약 상태·HTTP
   상태를 확인한다. HTTP 결과는 pg_net의 다른 요청을 포함할 수 있으므로 시험 요청 ID와 대조한다.
   SQL dispatch 성공만으로 HTTP 성공을 판단하지 않는다. 점검 출력에 cron.command·헤더·비밀값을 포함하지 않는다.

실행 누락, 2xx 이외 HTTP, 시간 초과, `stopped=DELETE_FAILED`, 증가하는 due 또는 2시간 이상
지연된 요청이 있으면 원인을 조사한다. 재시도를 위해 요청을 취소하거나 14일을 다시 시작하지
않는다. 장애 복구 후 기존 요청을 처리한다. 처리 중 플래그를 끄면 요청은 보존되지만 실제
삭제는 중단되므로 비활성화는 장애 대응 용도로만 사용한다.

## 검증과 출시 구분

- `pnpm typecheck`, `pnpm lint`, `pnpm test` 및 Deno `check`를 실행한다.
- `node scripts/account-actions-db-regression.mjs`는 운영과 분리한 임시 PostgreSQL/Auth에서
  전체 마이그레이션, 14일 대기, PIN 만료, 장애 후 삭제, 취소 경합, 영수증, FK cascade,
  실제 Auth 삭제·기존 토큰/갱신 거부를 검증한 뒤 테스트 자원을 제거한다.
- `supabase/tests/durable_account_deletion.sql`은 장기 장애·PIN 발급 시 삭제 기록 보존·
  처리 중 재요청 거부·재시도 우선순위를 검증한다. 운영에서 테스트용 시각을 조작하지 않는다.
- 운영 검증은 대상 0건 확인 후 pg_net → 실제 `/purge` 요청, 인증 없는 삭제 거부,
  알 수 없는 영수증의 최소 응답, RPC 권한과 배포 이력으로 수행한다.

앱 코드·운영 자동 삭제의 완료가 스토어 출시 심사 완료를 뜻하지는 않는다.
[Apple 안내](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)는
앱 안의 계정 삭제 경로와 소요 시간·완료 안내를 요구한다.
[Google Play 안내](https://support.google.com/googleplay/android-developer/answer/13327111)는
앱 안 경로 외에도 앱을 다시 설치하지 않고 삭제 요청을 할 수 있는 웹 리소스를 요구한다.
공개 웹 삭제 요청 주소, 공개 개인정보처리방침의 백업·로그 보관 설정, 문의 담당 및 실기기
Google 계정 검증은 스토어 출시 때 별도로 확인해야 한다. 이 문서는 공개 법률 고지나
스토어 정책 준수 인증을 대신하지 않는다.
